## 结论先行

- **A：未证实预算扩容引起 HTTP 500/529。** 预算限额用于 ATR 本地预检、上下文裁剪和 Run 循环控制，没有作为字段传入模型 Worker 的供应商请求。单次输入上限仍为 30000。工具上限会通过预采集数量间接影响上下文，但本业务目标只有 2 个已确认服务映射，旧、新上限都会选中同一组服务。
- **B：没有发现模型请求调用链的本地回归。** `model.py` 与 `model_worker.py` 的模型请求构造、超时传递和零重试路径没有随预算扩容改变。扩容提交只提高 Settings/BudgetLimits 的上限校验；默认值没有变化。四项容错测试失败来自测试仍把“局部隔离的跨目标反证”当成全局硬错误。本专项只修正了这两处测试，未改生产校验逻辑。
- **C：已证实 ATR 收到真实 HTTP 529、500、500 响应，尚未证实上游固定 100 秒超时。** 失败网络耗时分别约 106.7、102.5、98.1 秒；因为客户端超时为 180 秒且审计中有真实 HTTP 状态，这不是 ATR 本地 120/180 秒超时。时间聚集值得让供应商查网关日志，但不足以证明其主动设置了 100 秒边界。
- **D：目前优先联系模型中转服务核查请求追踪，不改代码、不继续扩预算，也不自动重试。** 可在供应商确认故障窗口后，再考虑用 20/50/300000 做一次有明确停止条件的对照；它是控制变量，不是已证明的修复。已核验的 15 调用成功 Run 实际快照为 20/50/200000，而不是 300000。

## HTTP 状态、超时与重试链路

调用链为 `Agent workflow → model.call_json → 独立 model_worker 子进程 → LiteLLM/OpenAI SDK/httpx → 配置的 OpenAI-compatible HTTP 端点`。

- `call_json` 把 `min(MODEL_TIMEOUT_SECONDS, Run 剩余执行时间)` 作为请求超时，并将 Worker 子进程硬超时设为请求超时加 10 秒：`model.py:45–55,115–139`。当前配置为 180/190 秒。
- Worker 把响应 hook 捕获到的 `response.status_code` 传入诊断；`provider_request_id()` 仅允许保存格式受限的 `x-request-id`/`request-id`：`model_worker.py:15–24,61–81,142–153`。HTTP 5xx 在 `model_errors.py:93–94` 分类为 `provider_unavailable`；没有 HTTP 状态的 SDK 传输 Timeout 才映射为本地 `model_timeout`（`model_errors.py:86–90`）。因此三个失败的 500/529 是 ATR 实际收到的 HTTP 响应，不是本地把 Timeout 合成为 500。
- OpenAI SDK `max_retries=0`、LiteLLM 请求 `num_retries=0`，记录中的 `retry_count` 全部为 0：`model_worker.py:110–124`。未发现隐藏的自动重试。
- 当前容器未配置 HTTP(S)/ALL 代理环境变量，Compose 也没有为 API 配置代理；历史 Run 没有保存当时容器代理环境或 HTTP 连接头，故不能完全排除运行环境层面的临时代理差异。
- 安全审计仅保留少量请求 ID，没有保留 `Server`、`Via`、`CF-Ray`、`Retry-After` 等响应头或响应错误正文。529 请求保存的可用追踪 ID 为 `abd13b23-eeb6-4ed7-9c94-c8baf8905c02`；两个 500 没有保存可用请求 ID。不能据此判断 500/529 是中转服务自身、它连接的模型供应商还是更前置网关生成，也无法确认队列拥塞、上游负载、策略拒绝或固定代理截止时间。

失败网络等待分别为 98.1、102.5、106.7 秒，客户端配置上限为 180 秒，三者先收到 HTTP 状态再结束。该分布与某个约 100 秒上游/代理限制相容，但范围横跨约 8.7 秒且只有 3 个样本，**没有证据证明存在固定 100 秒边界**。失败状态和 `provider_request_id` 足以证明端点响应，不足以定位其内部来源。

## 请求复杂度、配置回归和上下文

1. **预算字段没有进入请求体。** `model.py:128–139` 的 `_completion()` 参数列表没有 Run 轮数、工具数或累计 Token 字段；预算只在发请求前影响准入。`max_rounds` 是外层 `workflow.py:339` 循环上限，`max_total_tokens` 是 `budget.py:109–119` 预检，均不改单次 HTTP JSON 参数。
2. **有间接上下文影响，但本案例没有扩大服务集合。** 工具上限通过 `business_investigation.py:331–335` 决定启动时要预取多少个映射。只读 SQLite 确认这几个 Run 的目标下恰有 2 个 `confirmed` 映射（API、DB），20/50 和 100/500 两组配置均会覆盖这 2 个映射；失败 Run 没有因 500 工具上限多预取其他服务。未来若某业务有超过旧预采集容量的映射，扩大工具上限可能间接改变首轮模型上下文，应单独评估。
3. **实际上下文随调查轮次变大。** Workflow 每轮构造当前证据、有限历史动作和假设摘要；上下文压缩在预算预检前执行。成功 Run 的本地估算最高到 24600，仍通过 30000 单次限制；三个失败估算均低于 30000。当前没有发现 schema 被重复拼接到多个消息的路径：system 消息含一份输出契约，user 消息为经过清理的上下文。
4. **输出限制不是失败证据。** 三个失败审计都只知道本地预留输出 1500，没有实际输出 usage。15 次成功调用输出实际为 266–859（更广的同配置失败 Run 前置成功调用最高 1328）；此数据不能证明供应商对失败请求的输出预算处理，也没有显示 ATR 在扩容时提高了 `max_tokens`。
5. **配置/代码差异的范围有限。** 成功后改动的是上限校验和 `.env` 中的最大 Run 轮数、工具数及累计预算；失败 Run 的 Run 快照确认这些新值生效。`MODEL_TIMEOUT_SECONDS=180`、单次输入 30000、输出 1500、reasoning low 与成功 Run 验收设定一致，但历史请求级数据库快照不包含后三项。端点摘要相同；不存在因配置文件误读导致调用不同 Base URL 的证据。

- 本专项把纠错测试改为未注册的预测枚举值触发严格校验；把全量拒绝测试中的跨目标反证用例移除，保留局部隔离的专门断言。未更改生产 Schema、校验器、证据门、工具授权或自动纠错次数。
