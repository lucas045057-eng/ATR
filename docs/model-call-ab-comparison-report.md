# ATR V2.2 真实模型调用 A/B 对照报告

实验日期：2026-10-10（表中起止时间与 ledger 使用 UTC，北京时间为 UTC+8）。目录：`E:\ATR`。所有真实调用仅使用合成数据；未启动正式 8 轮故障调查，也未向调查数据库写入实验结论。

## 1. 结论与修复边界

1. 原路径的完整调查对照，两侧均在请求发送后长时间等待，最终 HTTP 529；没有发现只有 ATR Worker 失败的证据。请求发送前 TCP/DNS、TLS 和初始化开销不能解释约 111 秒等待。
2. 已复现独立的供应商拒绝原因：HTTP 400、`invalid_request_error`、固定安全原因 `model_price_not_configured`。ATR 原提示将其泛化为输出兼容性问题；现在以固定中文提示显示“模型供应商报告模型价格未配置，请联系供应商管理员”。这个提示准确转述供应商报告，不能证明后台计费配置的内部状态。
3. 未显式设置推理强度的完整 Responses 请求，两次均在 120 秒读取超时。相同完整上下文与严格 Schema，显式 `low` 后，Responses Worker / 直连以及 Chat 直连 / 正式修复 Worker 均返回 200 并通过严格校验。修复后的 Chat 对照：Worker **55.25 秒**，直连 **47.73 秒**。
4. 最小正式改动是可显式配置推理强度；保持原 Chat 路径和 120 秒超时。增加可选 Responses 支持，按供应商协议映射 `input`、`text.format`、`max_output_tokens`，不自动切换或重试。响应不完整、拒绝、原生工具调用、无效动作/引用均停止。
5. **尚不能断言历史超时的唯一根因是默认推理强度，更不能声称默认一定为 high。** 上游默认值与处理队列不可见；顺序、负载、缓存及供应商路由/计费差异仍是实验局限。证据定位到请求发送后等待响应阶段，无法区分网关、执行排队或链路内部情况；显式低推理强度方案已有重复成功记录。

## 2. 环境与两条路径

- 同一原 API 容器 `atr-runtime-api-1`、模型 `gpt-6.1-sol`、现有 `.env` 凭据和 `https://xfastapi.ai`；host/container 的模型、Base URL、密钥与超时只做安全等值核对，不输出密钥。
- Python 3.12.14；httpx 0.28.1；httpcore 1.0.9；OpenAI SDK 2.54.0；LiteLLM 1.104.1；Pydantic 2.13.5。
- HTTP_PROXY / HTTPS_PROXY / ALL_PROXY / NO_PROXY / SSL_CERT_FILE / SSL_CERT_DIR 均未设置。连接均是冷客户端；两侧相同 120 秒 HTTP 各阶段超时与 130 秒外层进程硬超时。
- A：httpx 直接 POST。B：复用 ATR `_completion` 的独立进程生命周期和原 Worker，LiteLLM completion → OpenAI SDK → httpx；实验子进程只注入安全观测。正式 API 进程未装入观测补丁。
- Responses 探针使用临时 LiteLLM Responses 隔离适配器；它不是当时的正式生产路径。#23 使用正式新 Worker 源码，整个 app 复制到原容器 `/tmp/atr-ab-patched`，按新的 PYTHONPATH 启动隔离进程；保持同一容器、网络和凭据，未覆盖当时运行 API 的源码。
- #23 实测后仅收紧了 Responses 保留路由的拒绝范围；gpt-6.1-sol 的 Chat 请求构造未再改变。最终完整测试与 Docker 验收覆盖交付源码。

## 6. 已证明与尚未确定

已证明：同容器同凭据下两条原路径可达到聊天接口；最小JSON两侧都成功；完整默认请求两侧均有长等待；原Worker实际路径与参数已核对；完整 low 消息在两种协议与独立进程通过严格校验；固定供应商价格错误原因可复现；严格拒绝机制没有放宽。

尚未确定：历史 run d8006d1b-3699-4c8d-83c2-5cb8749be3fd 的特定上游根因。历史审计只有 initialize3761.403ms / network120935.216ms / total124870.41ms / request / HTTPNone / retry0 / usage estimate，没有原始请求/响应。当前实验不能还原历史失败字段，也不能证明全部400都是价格错误：#1–#6没有保存固定reason，只有#10/#11/#12有安全原因证据。不能根据 /v1/models 的403断言chat被拦截。

没有直接证明：LiteLLM Bug、上游默认为high、模型真实后端身份、价格配置实际内部状态、hidden Prompt内容、任何真实业务故障根因，或未来不会偶发超时。

## 7. 本地修复与验收

- 新增 `MODEL_REASONING_EFFORT`，显式配置时分别映射到Chat的reasoning_effort或Responses的reasoning.effort；未配置保持原行为。当前最小运行方案是原Chat协议 + low，不提高正式120秒超时、不修改模型/Base URL/密钥/授权范围。
- `MODEL_WIRE_API` 默认 chat_completions；responses 为显式选择。仅允许已验证的 openai/<原始模型名> native路径，拒绝其他provider和SDK保留路由；不自动bridge/fallback或补发付费请求。
- Responses 只有完成状态、无error、无incomplete_details且纯assistant output_text才能进入原JSON解析器和严格验证器；refusal/native工具调用/截断/非法动作与引用全部拒绝。actual来自原始input/output整数。
- 价格配置错误只匹配已核验HTTP400 + invalid_request_error + 固定短语，在内存识别后仅输出固定reason与中文消息；认证/限流/服务故障分类不被覆盖。页面沿用现有ModelError组件，Mock Chrome已验证新提示与恢复。
- 证据门、工具白名单、store授权范围、Schema、正式调查Prompt、消息压缩规则保持不变。通过Schema只证明模型输出合法；实验未执行输出中的工具，也未将其视为业务根因成立。
- 离线RED→GREEN覆盖协议映射、真实usage、拒绝与截断、非法动作、保留路由、原Chat配置兼容。价格测试RED2失败→GREEN5通过；协议初次RED7失败→GREEN10通过；审查补充拒绝用例也先失败再通过。
- Docker Mock：原Chat与最终Responses分别10个合成场景，合法/null/fenced通过独立证据门；非法类型/引用/动作/额外工具参数/角色拒绝；529、价格400安全停止。Chrome真实页面核验字段级错误、价格提示、无敏感值。另在最终Docker镜像检查两种桥接路由于initialize停止、无HTTP。


最终完整测试：**304 passed，0 failed/errors/skipped**；全仓 F/E9 检查通过。价格修复阶段另一次完整290通过；中间两轮因审查发现需补守卫主动中断，不计为通过，最终完整套件重新运行。
