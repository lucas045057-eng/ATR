# P0：模型故障时的只读事实调查

适用于本地 `codex/ab-v1.1` 分支中的 `ab_v1` 协议。没有改用旧的业务调查循环，也没有改变其它协议的模型故障策略。

## 调查顺序

Runtime 根据冻结的事故、图版本、目标授权和当前有效服务绑定，先从既有候选生成器中选择状态、日志及精确授权健康端点的基础检查。每次只执行一个已有 action，仍通过 `BusinessToolRegistry` 和连接器策略核验。

基础工具和当前任务对象范围在应用候选数量上限之前筛选，避免其它目标、配置或源码候选挤掉必要状态与日志。离线配置候选只来自实际端点合同缺口的对象，旧日志缺口不能扩大配置读取范围。动作历史继续去重：已执行的动作不自动重放，失败、拒绝、旧日志也会留下记录。连续两项无新信息不再提前放弃其余基础检查；有限候选耗尽后才进入推理阶段。没有已确认对象时继续使用原发现和人工范围确认流程。

如果当前独立证据已经通过原证据门，Runtime 可以直接结束。否则才请求 AI 决策。首次模型异常即保存安全诊断和失败调用位置，转入离线阶段；之后所有推进步骤都不会再调用模型。529、其它 5xx、连接失败、超时，以及不能安全使用的模型输出都遵守这一停止策略。SDK 的零自动重试设置保持不变。

离线阶段优先完成剩余基础检查，再按后端缺项选择现有授权只读候选。端点合同缺口可以触发授权目录的配置发现和读取，不能生成命令、URL、SSH 目标或自行批准映射。若没有可满足缺项的合法候选，就完成事实报告并保留缺口。

## 约束和终态

每次读取仍核验 Run、目标、授权摘要、服务/容器/进程绑定及租约。工具调用、返回证据和模型 usage 沿用原数据库记录、预算 ID 与授权检查。取消、失效租约、现有预算管理器拒绝及单次超时不会被绕过。当前分支预算为 `accounting_only`，累计次数与总时长参考值不执行限制；P0 没有重新启用这些历史额度。单次模型最多 45 秒、原 SSH 读取最多 10 秒，以及连接器更短的限制继续适用。

完成离线采集和报告生成记为执行 `completed`，模型仍明确标记 `failed`，分析模式为 `offline`。诊断状态独立保留 `partial` 或 `unresolved`；执行结束不代表 `completion_satisfied`，也不会开放未确认根因的修复入口。已有失败 Run 的恢复、备用模型、收费重试和主动模型探针不属于 P0。

## 报告合同

`summary.report.fact_report` 使用 `ab-fact-report-1`，包含已确认事实、直接异常、未知原因、缺失证据、检查结果及下一步建议。事实带原 call ID、evidence ID、对象和观测时间，HTTP 事实和检查保留具体授权端点标识与 URL；不复制原始敏感日志或供应商错误正文。模型错误单独描述模型服务，不能成为业务故障根因。原模型未知项保留为待核实建议，关键资料冲突也列入未知项和缺项，不因完整机制已通过而隐藏其它未解释的问题。

每项检查分别记录工具状态（成功、拒绝、失败、超时、未执行）和证据状态（当前取证、已过期、事故窗口外、不足以核验、缺失）。成功读取旧日志不代表获得当前故障证据；无可靠时间、启动身份、完整输出或原目标 HTTP 身份时保留缺口。窗口外日志不会支持根因，也不能冒充当前健康日志。

每次保存和最终结束前重新执行原 `ResultEvaluator`，防止沿用过期或图谱变化前的缓存结果。`MechanismRegistry` 的完整链、独立引用、端点合同、反证及冲突规则没有放宽。前端展示确定性事实摘要和检查状态，模型故障提示不会覆盖当前已采集事实。

## 隔离验证

新测试使用临时数据库和明确标识的 Mock 运行目标，覆盖两组陌生业务服务名及大范围候选。模型传输使用测试替身和真实回环 HTTP 529 服务；实际模型 worker 和调用审计也纳入测试，不连接付费供应商。浏览器用专用回环 API、临时数据和本地模型服务验证故障事实页面。生产服务器不用于故障注入。

针对性命令：`pytest tests/ab_v1/test_offline_investigation.py tests/e2e/test_ab_offline.py`。完整验证仍使用项目 `pytest`、Ruff 与前端构建；环境或历史失败需单独报告，不能将 P0 通过称为整体 A+B 验收通过。
